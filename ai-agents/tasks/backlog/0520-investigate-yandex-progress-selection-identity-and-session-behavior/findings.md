Yandex advises pausing sync on open, then returning to the menu or restarting and fetching the player again on close. The example uses `getPlayer()` then `getData()`. The section does not specify per-choice ID/auth outcomes, a choice/old-ID/new-ID payload, exactly-once delivery, ordering relative to authentication promises, automatic iframe reload, or an old-to-new ownership proof. **D3 — [In-app purchases](https://yandex.com/dev/games/doc/en/sdk/sdk-purchases).** `getPayments({signed:true})` provides signed purchase responses; `purchase()` opens the payment frame, resolves on success and rejects on cancellation/failure. `getPurchases()` handles unprocessed and non-consumable purchases. `consumePurchase()` permanently deletes a processed purchase. ## Established gaps versus hypotheses

**Established:** absent selection lifecycle; plain-player caching; independent signed/session/payment state; no identity fence around login/read/purchase completion; page-scoped reconciliation/held/grant state; known-ID match overwrite refused; no trusted automatic historical-identity linking. These are integration constraints, not proof all caches are stale in the real SDK.

**Plausible, not reproduced:** selection without iframe reload leaves A/P in client while SDK moves to B; plain/signed snapshots disagree and login becomes unverified; late A results republish after B; existing match retains P while UI follows Q; a purchase started for P completes while Q is displayed. If the iframe actually reloads before these windows, that branch may avoid page-state skew. If B is unmapped, even a perfect fresh boot can still reach an empty Q.

**Unsupported:** which choice caused this incident; universal ID change on either choice; logout on either choice; guaranteed automatic iframe reload; old SDK objects always staying stale or always updating; getPurchases spanning all historical identities; a signed B proving A ownership; browser-history similarity authorizing merge; the recovery merge proving dialog causality. Permanent consumption is disabled in current source (`src/profile-server/ConsumePermanentSetting.ts:11`), but that is neither a dialog fix nor independent deployment verification.

These estimates cover client safety, **not** a new backend linking system. Automatic reload on every close is another policy choice, not implied by the recommendation. It would also conflict with existing purchase/match protections unless deliberately constrained.

**Constraints kept:**

- **D3** (`ProfileSession.ts` header; `GameRestart.ts`) makes failed login final for the page and permits specific player-initiated recovery surfaces. `requestGameRestart` has no purchase-dialog guard of its own. A selection handler must not silently reset the failure latch, auto-retry it, or reuse the login-success event to invent authorization for reload.
- **AR-9** (`src/client/ProfileSession.ts:312`, replaced-token branch) intentionally returns a newer token without checking account again. Any in-page identity rebinding re-raises this accepted residual. A restart-only flow can avoid rebinding but must prove stale callbacks cannot reach this branch during deferral; otherwise AR-9 also needs an owner ruling.
- **ADR-125** preserves guest “Log in and buy” continuity and post-grant Restart/Later. If selection can occur inside that auth flow, restart-first may intentionally interrupt it. The owner must choose that exception; this report does not silently change it. Do not cut off a charged purchase's completion; suppress its stale UI effects without discarding recovery evidence.
- **ADR-113/116/121/124/126/128:** current identity proof, verified paid reads, signature-age rules, game-server vouch and manual purchase-transfer boundaries stand. A held purchase is a block/contact signal, never permission to transfer. Match state/crediting cannot be reassigned from A to B merely on a client event.
- **ADR-122:** 0394 gates nothing. 0394 is broader general-account-switch context; 0424 is broader ID-change context. No activation, dependency, sprint or status change proposed here.

**Smallest independently reviewable implementation candidate:** one selection safety flow using the recommended restart approach, bounded to the facade event seam plus a shared transition guard at profile, purchase, join and UI-publication boundaries. It must include deferred/busy behavior, not just `getPlayer()` on close. Keep backend identity resolution/grant ownership unchanged. Likely change surface: facade, `ProfileSession`, card/status publication, reconciliation/coordinator/product continuation guards, `Main`/join setup and restart/dialog-presence integration. This is a scope proposal for a separate approved brief/plan; no `plan.md` or approved-plan claim is created here.

**Acceptance to put in that later plan:**

1. Both close-with-open and close-without-open enter safety; duplicates/repeated SDK arrival produce one transition/restart request, no accumulating listeners or reload loop. Missing close or failed/hung refresh never silently resumes purchases on uncertain identity; offer the approved recovery at a safe point.
2. Deferred A login/read/reconcile/payment-refresh/grant UI results cannot republish after transition. A queued 401 cannot retry a B operation using A credentials. Preserve D3 and explicitly record the AR-9 disposition; do not call test-reset helpers as production invalidation.

4. No new payment opens once transition begins, including a late intent result and guest auto-continue timer. An already charged completion remains bound to its original intent and idempotent recovery; no grant is retargeted or falsely published for a new identity.
5. No automatic interruption of lobby/join/match/payment; test the approved deferral, storage-disabled/latched paths, stale callbacks and any retained match/reconnect state. Document old-match XP policy; never implement known-ID overwrite as a side effect.
6. Reuse relevant existing test files. Add real event/transition/race cases under the future approved scope; unit tests assert local guards, and owner-run Yandex checks below establish actual event/reload/signature timing. Neither can substitute for the other.
