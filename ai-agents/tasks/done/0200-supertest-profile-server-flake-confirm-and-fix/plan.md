### 0.2 🆕 A fifth symptom, and it is strictly more diagnostic than the four in the brief

probe 2 run 33, `tests/profile-server/NameChangeRoutes.test.ts:405`:

```
● name-change routes › GET /v1/profile projection › merges the name-change state when there is one

    expected 200 "OK", got 401 "Unauthorized"

      at Test._assertStatus (node_modules/supertest/lib/test.js:309:14)
```

The same run also carried a `PaymentsRoutes.test.ts` `Exceeded timeout of 5000 ms` on the CORS/OPTIONS
preflight test — i.e. **two of the family in one run**.

**Why the 401 matters.** `GET /v1/profile` is registered at `src/profile-server/Routes.ts:255-284` as:

```ts
app.get("/v1/profile", allowPublicCors, profileReadLimiter, async (req, res) => { … });
```

Its only exits are **400** (`bad_request`), **404** (`not_found`), **200**, and **500**
(`internal_error`). `internalAuth` — the only 401 source in the file — guards `/internal/*` routes
exclusively. **No code path in this app can answer `GET /v1/profile` with 401.**

So the client read a `401` that the app it was talking to could not have produced. That is **positive
evidence of misdelivery or response cross-talk**, and it is a strictly stronger observation than the
brief's four symptoms, all of which are also consistent with "the request never arrived". It also
sharpens the brief's own reasoning: the brief inferred one event from *absence* (no CORS header, an
unexpected 404); this is the same event caught *producing a response that belongs to someone else*.

**Deferred to the producer, not corrected here:** the brief's symptom table should gain this row.
Briefs are the producer's file (same handling `0197` used for its off-by-one finding).

### 0.3 One hypothesis is already refuted — by inspection plus one probe, no sweep runs spent

**H-F — supertest/superagent reuses pooled keep-alive sockets, so a recycled ephemeral port hands a
request to whatever now listens there.** This was the most attractive mechanism on paper (Node ≥19 sets
`http.globalAgent` to `keepAlive: true, timeout: 5000` — and 5000 ms is exactly the observed timeout).

**REFUTED.** `superagent` sets `this._agent = false` (`node_modules/superagent/lib/node/index.js:162`)
and passes `options.agent = this._agent` (`:736`). `agent: false` makes Node create a throwaway agent
per request — **no pooling**. A direct probe confirmed every response carries `connection: close`:

```
node v24.13.0 globalAgent.keepAlive= true  timeout=5000
0 status 200 connection-hdr close elapsed_ms 8
1..4 status 200 connection-hdr close elapsed_ms 1-2
```

The matching `5000` is a coincidence of two unrelated defaults: jest's default per-test timeout is also
5000 ms, so **every** hang in a supertest test reports as "Exceeded timeout of 5000 ms" regardless of
cause. **Do not read the 5000 as a fingerprint of the agent timeout.** Recording this negative is worth
roughly 200 sweep runs that will not now be spent.

### 0.4 A hang was observed, and it is probably a *consequence* of the flake

probe 1 printed `Jest did not exit one second after the test run has completed` and then hung until
killed at 10 minutes. Probe 2 used `--forceExit`, which masked it (0/40 warnings).

**Predicted mechanism, to be tested in Phase 1, not asserted here.** `supertest`'s `Test.end()`
(`node_modules/supertest/lib/test.js:133-160`) calls `server.close(...)` **inside** superagent's
response callback. When a request never completes, that callback never fires, so the ephemeral server
is **never closed** and stays bound — the jest worker cannot exit. If true, the hang is the same defect
seen from a third angle, and `--forceExit` in any harness will hide it.

⚠️ `CLAUDE.md` states that a hanging test suite is "a real regression — investigate it, don't add the
flag back." That sentence is scoped to `test:integration`. This hang is on the **unit** path. The rule's
*spirit* applies: **`--forceExit` may be used in throwaway measurement harnesses only, and must never
reach `package.json`.**

**Also ruled out for the hang:** `express-rate-limit@7.5.0`'s `MemoryStore` `setInterval` is `.unref()`'d
(`dist/index.cjs:443-447`), so the ~95 limiter timers per run cannot hold the process open.

### 0.5 One imprecision in the brief's reasoning (its conclusion still stands)

The brief says the `404`s are "not route-registration bugs" because the routes are registered
"unconditionally". They are in fact registered **conditionally**:
`if (paymentsRepo !== undefined)` (`Routes.ts:400`), `if (inbox !== undefined)` (`:592`),
`if (nameChange !== undefined)` (`:734`). The failing tests all pass a repo, so the conditions hold and
**the brief's conclusion is correct** — but the stated reason is not, and Phase 1 must not lean on it.
Note also `Routes.ts:836` (`POST /internal/v1/name-change/decide`) has its **own** `404 no_pending`
exit, so a `404` on that path is genuinely ambiguous between "express default 404" and "the route
answered 404" until the body is captured. **This is exactly why brief step 3 (capture the wire, not the
assertion) is the load-bearing step.**

## 2. Phase 1 — confirm the mechanism

### 2.1 The instrumentation (brief step 3) — do this FIRST, it is the load-bearing step

Everything else is rate-counting; this is the step that turns the hypothesis into a finding or kills
it. Build a **throwaway** harness that runs under `NODE_OPTIONS=--require <shim>` so that **no test
file and no source file is edited**:

The shim monkey-patches, at require time:

1. `net.Server.prototype.listen` — record `(pid, serverId, assignedPort, timestamp)` for every bind,
   and `close` for every unbind. This yields the **per-process port history**, which is what decides the
   port-recycling hypothesis.
2. `express` app creation — insert a first middleware on every app that logs
   `(pid, serverId, method, url, headers.origin, timestamp)` **before any route matches**, and an
   `res.on("finish")` logging the status the app actually sent.
3. `supertest`'s `Test` — record the URL it computed (hence its target port) and the status/headers/body
   the client observed, plus elapsed time.

Emit one NDJSON line per event to a file keyed by pid. **No credential values are ever logged** — log
header *names* and `Authorization: present|absent`, never the value (brief verification 7).

Then run the cheap harness in a loop until it reproduces, and for the reproducing run answer:

| Question the trace answers | What each answer means |
|---|---|
| Did the intended app's first middleware fire at all? | **No** ⇒ the request went elsewhere or never arrived. **Yes** ⇒ misdelivery is dead; look at the response path. |
| If it fired, what status did *it* send? | Server sent 200, client read 401 ⇒ **response cross-talk**, confirmed. |
| Was the target port previously bound in this same process? | **Yes** ⇒ port recycling is implicated. **No** ⇒ H-B is refuted for that occurrence. |
| Was the target port bound *concurrently* in another pid? | Distinguishes intra-process from cross-worker. |
| For a 5000 ms timeout: does the request ever complete if the timeout is raised to 60 s? | **Completes** ⇒ late, not lost (H-D) — the brief's "raise the timeout" candidate becomes legitimate. **Never** ⇒ lost. |
| For a `404`: is the body express's default HTML or `{"error":"no_pending"}` / `{"error":"not_found"}`? | Separates "no route matched" from "the route answered 404" (see §0.5). |

⚠️ **Do not filter output.** Every run tees complete stdout+stderr to its own file. The brief is
emphatic about this and it has already cost one lost identity; probe 2's 1-in-40 hit is only nameable
because the full log was kept.

⚠️ **Watchdog required.** `timeout(1)` / `gtimeout(1)` are **not installed on this machine** (verified).
Each loop iteration must carry its own kill (background the run, sleep, `kill` if still alive) so one
hang does not consume the whole budget — probe 1 lost 10 minutes exactly this way. Do **not** solve it
with `--forceExit` alone: that hides §0.4.

### 2.2 The `--runInBand` discriminator (brief step 1), with its power stated

| Arm | Command shape | N | Purpose |
|---|---|---:|---|
| Control | `npx jest` (parallel, 13 workers) | 200 | Re-establish the baseline rate on *today's* tree |
| Serial | `npx jest --runInBand` | 200 | The discriminator |

**Power, stated rather than assumed.** At the brief's p = 0.053:
- N = 30 → P(zero failures) = 0.947³⁰ ≈ **19.6 %**. A zero result at N=30 proves nothing. The brief is right.
- N = 100 → P(zero) ≈ **0.42 %**.
- N = 200 → P(zero) ≈ **0.002 %**.

**Reading a negative.** Rule of three: 0 failures in N runs gives a 95 % upper bound of ≈ 3/N.
0/100 ⇒ ≤ 3 % (only about half the pre-rate — weak). 0/200 ⇒ ≤ 1.5 % (a ≥3.5× reduction — meaningful).
**N = 200 is the number this plan uses**, both here and for post-fix verification, and 200 serial runs
cost ~17 min (measured 4.94 s/run), 200 parallel ~9 min.

**Confound to state, not to hide.** `--runInBand` changes **two** variables: parallelism *and* the
execution context (main process vs a forked worker). A graded control removes the ambiguity and is
nearly free: also run `--maxWorkers=2` and `--maxWorkers=8`, N=100 each (~4 min each). A **dose-response
in the rate** implicates contention; a flat rate that collapses only at `--runInBand` implicates the
worker context instead.

⚠️ **Already-known partial refutation.** probe 1 and probe 2 reproduced with **4 workers on 4 suites**,
and `0197`'s sweep B reproduced with the jsdom suites excluded. Whatever this is, it does **not** need
13 workers or ~95 servers per run. The parallel-contention story is therefore *weakly* supported going
in; the discriminator must be able to say so.

### 2.3 The standalone per-suite loops (brief step 2)

Each of the four suites alone, ×100 (`~1.1 s/run` ⇒ ~2 min per suite, ~8 min total). Record the
per-suite rate; an unequal rate is a clue (the brief's own point). Add a fifth arm — **the four suites
together at `--maxWorkers=4`, ×200** (~8 min) — because that is the harness already shown to reproduce.

Prediction worth stating in advance: if a suite alone is `0/100` while the four together reproduce, the
mechanism needs **more than one process binding ephemeral ports at once**, which is the port-recycling
family. If a single suite alone reproduces, it is **intra-process**, and that is a much smaller search.

### 2.4 The port-reuse / exhaustion question (brief step 4)

Answered directly by §2.1's bind log, plus:
- `sysctl net.inet.ip.portrange.first/last` and `net.inet.tcp.msl` — the ephemeral pool size and the
  `TIME_WAIT` (2×MSL) window on this host.
- `netstat -an | grep -c TIME_WAIT` sampled during a run, to see whether ~95 bind/teardown cycles
  actually accumulate `TIME_WAIT` state.
- Already recorded by inspection: supertest binds `:0` (`lib/test.js:63`), and closes each server in
  the response callback (`:133-160`) — so servers *are* closed on the happy path, and are **not** closed
  when the request never completes (§0.4).

### 2.5 Hypothesis ledger — every hypothesis, its prediction, and what would FALSIFY it

The brief asks specifically for falsification criteria. A plan that can only confirm is not an
investigation.

| # | Hypothesis | Predicts | **Falsified if** |
|---|---|---|---|
| **H-A** | Contention between parallel jest workers | Rate collapses to ~0 under `--runInBand`; dose-response across `--maxWorkers` | It reproduces under `--runInBand` at a comparable rate, or the rate is flat across worker counts. *(Already weakened: reproduced at 4 workers.)* |
| **H-B** | Intra-process ephemeral-port recycling: `listen(0)` re-hands a port whose previous connection is not fully dead | Failing requests target a port previously bound in the same pid; the intended app's first middleware never fires | Failures land on ports never before used in that process, **or** the intended app *did* receive and correctly answer the request |
| **H-C** | Response cross-talk: the client reads a response belonging to a different request | Server-side status ≠ client-observed status on a failure (e.g. app sent 200, client read 401) | Server-side and client-observed statuses always agree on every captured failure |
| **H-D** | Late completion, not loss | A request that trips the 5000 ms timeout completes if given 60 s | Instrumented requests never complete at any timeout ⇒ the "raise the timeout" candidate is dead and must not be used |
| **H-E** | Transient machine-local condition, not a repository defect | No correlation with port history; rate tracks machine load; no server-side evidence | Any of H-B/H-C/H-D confirmed. ⚠️ **Cannot be positively proven on one host** — if this is where we land, it is reported as the honest ceiling, exactly as `0197` reported H6 |
| **H-F** | Pooled keep-alive socket reuse | — | **ALREADY REFUTED** (§0.3): `superagent` sets `agent: false`; responses carry `Connection: close` |
| **H-G** | The hang is a *consequence*: a timed-out request leaves its ephemeral server unclosed | A reproducing run under `--detectOpenHandles` names an open `Server` handle | `--detectOpenHandles` reports zero open handles on a reproducing run ⇒ the hang is a separate defect and needs its own line in the findings |

**Negatives are findings and get written up** (brief step 5), H-F included.

### 2.6 Stopping rule

- **Reproduction achieved and traced:** stop measuring, write the finding. Two clean traces of the same
  mechanism are enough; a third buys little.
- **If it does not reproduce at all:** the pre-registered ceiling is **500 cheap-harness runs**
  (~20–25 min) **plus** 200 full-suite parallel runs (~9 min). 0/500 gives a 95 % upper bound of ≈0.6 %,
  i.e. an order of magnitude below the brief's 5.3 % — which would itself be a real finding: *the rate
  changed on this tree*, and the honest report is "did not reproduce at ≤0.6 %; the earlier 5.3 % was
  measured on a different tree/host state." **Do not silently extend the budget** — coming back for more
  is an owner decision, as it was in `0197` (ruling R3).
- **If it reproduces but the trace is inconclusive** after two captured occurrences: stop, report H-E
  with the traces attached, and recommend the recognition note (§3.4) rather than a fix. Do **not**
  manufacture a mechanism to justify Phase 2.
- **Machine load is a confound** (`0197` §3.1 hints at it). All sweeps run on an otherwise-idle machine;
  any run overlapping other work is recorded as such, not silently pooled.

## 3. Phase 2 — conditional on Phase 1, deliberately not pre-committed

No fix is chosen here. Each branch names what evidence selects it and what it costs.

### 3.1 If H-B / H-C confirmed (port recycling or response cross-talk)

**Direction: stop binding ~95 ephemeral servers per run.** Bind **one** server per suite in `beforeAll`,
close it in `afterAll`, and point `request()` at that server. Collapses ~95 binds/run to 4 and removes
the recycling surface entirely.

Two things must be got right, and both are real work, not a mechanical edit:

1. **supertest's own semantics change.** `serverAddress` (`lib/test.js:57-68`) takes the
   `if (!addr)` branch only for an *unlistened* server. Hand it an already-listening `http.Server` and
   `this._server` stays undefined, so `end()` will **not** close it (`:141`). The suite must then own
   `afterAll(close)`. Getting this half-right leaks a listener into every run.
2. ⚠️ **Test isolation is at stake.** Every test today builds a *different* app —
   `appWith(mockPaymentsRepo({...}))`, `appWith(null)`, `createApp(mockProfileRepo())` — precisely to
   exercise different wirings (fail-closed paths, missing repos, bad secrets). A single shared server
   cannot serve them without either swapping mocks behind a stable app or grouping tests by app shape.
   **A change that quietly reduces the number of distinct app configurations under test is a deleted
   test, not a fix** (brief verification 5). If the refactor cannot preserve every configuration, it
   comes back to the owner rather than being trimmed to fit.

**Lighter fallback if the above is too invasive:** a shared `withApp(app, fn)` helper that awaits an
explicit `listen` and guarantees `close` in a `finally`. This fixes the **leak** (§0.4 / H-G) but does
**not** reduce the number of binds, so it does not address H-B. Its value depends entirely on which of
the two Phase 1 confirms.

### 3.2 If H-D confirmed (requests complete late, not never)

Raising the per-test timeout becomes defensible — but only:
- with the **measured completion-time distribution** attached (if the tail is 5.2 s, a 15 s timeout is
  reasonable; if it is 45 s, a timeout is papering over something), and
- scoped to the affected assertions, not applied suite-wide, and
- ⚠️ named as **partial masking**, since it makes the symptom invisible without removing the cause.

If H-D is **refuted**, this candidate is dead and must not be used to make the red go away.

### 3.3 If H-A confirmed (worker contention) — SURFACE, do not decide (brief item 7)

The owner-facing numbers, **measured today, not estimated** (brief verification 6):

| Configuration | Full suite wall clock | Delta |
|---|---:|---:|
| `npx jest` (parallel, 13 workers) | **2.36 s** | — |
| `npx jest --runInBand` | **4.94 s** | **+2.58 s (~2.1×)** |

That is the permanent, every-run cost of a suite-wide `--runInBand`, on a 14-core M4 Pro — the *best*
case; a slower or fewer-core machine will be worse, and this number must not be quoted as universal.
A `--maxWorkers` cap sits between the two and its cost will be measured before it is proposed.

**This is a product-cost decision. It goes to the owner with the number attached; the coder does not
take it.** Same warning `0197` carries, same reason.

### 3.4 If H-E (transient / machine-local)

No code change. Deliverable is the findings report plus a short **recognition note** — the family's
signature (`socket hang up` / 5000 ms timeout / unexpected `404` / missing `access-control-allow-origin`
/ **`401` on a public route**), the fact that it is confined to the four supertest suites, and the
instruction to re-run explicitly and say so rather than filing it as a segfault. That note is the
concrete thing that stops the `0068` misrecording from happening a third time, and on its own it may
justify the task even with no fix.

### 3.5 Forbidden in every branch (brief item 8)

**No retry.** Not `jest.retryTimes`, not a wrapper, not a loop inside the test. A retried flake is an
invisible flake. If a retry ever looks genuinely right, it comes back to the owner with that cost
named — it is never taken as an implementation detail.

## 6. Risks and non-obvious failure modes

1. **Instrumentation changes the timing and the flake disappears.** A `--require` shim adds work on
   every bind and request. *Mitigation:* run an instrumented control loop first and confirm the rate is
   unchanged before trusting a negative from an instrumented run. **If instrumentation suppresses it,
   say so — that is itself evidence for a timing-sensitive race.**
2. **`--forceExit` in the harness hides §0.4.** Needed to stop one hang eating the budget; it also masks
   the leaked listener. *Mitigation:* run both arms — with and without — and count the
   `did not exit` warnings separately.
3. **Only 2 occurrences captured so far.** A mechanism inferred from one trace can be wrong; that is
   how `0068`'s `SIGSEGV` misrecording happened. *Mitigation:* two independent traces of the same
   mechanism before calling it confirmed.
4. **Fixing the leak (§3.1 fallback) may hide the flake without fixing it** — if the leaked listener is
   part of the port-recycling mechanism, closing it promptly could suppress the symptom while leaving
   the race. *Mitigation:* the post-fix sweep must be run on the *original* harness shape, and the
   mechanism must be explained, not just made green.
5. **One host.** Restated, not buried: every result is machine-local. H-E cannot be positively
   established, only left standing.
6. **The `0197` segfault may fire during these sweeps** (~0.5 %/run; ~1300 runs ⇒ several expected).
   It is a **different** family. *Mitigation:* count `node-*.ips` crash reports before and after every
   sweep and classify any `SIGSEGV` run separately. **Do not let a segfault contaminate this flake's
   rate, and do not invent one root cause for both** — that conflation is the specific mistake this
   task exists to stop repeating.
