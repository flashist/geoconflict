## Accepted residuals (shared, do-not-re-litigate)
- Forged citizen identity can unlock private lobbies — What: the start gate trusts the client-asserted Yandex id through `getCreditableYandexId`; `isCitizen` is also visible on the unauthenticated lobby poll (`0068` R3) · Why (structural): no verified platform identity until `0267` / the Yandex secret key; the perk is a convenience; owner ruling 2026-09-26 "Accept for now (Recommended)" (brief § *Accepted residual — forged citizen identity can unlock private lobbies*) · Re-raise only if: private lobbies gain value beyond convenience (rewards, ranked, anything paid or scarce), or abuse is seen, or a call site reads `client.yandexPlayerId` directly, bypassing the funnel (ADR-103).
- Switch hides, server secures — What: the `private_lobbies` Yandex flag only controls whether the row is visible; the server gate runs whether it is on or off · Why (structural): the server cannot read Yandex flags; owner-approved plan § *Summary* ("The switch cannot secure anything") · Re-raise only if: a server-readable feature switch is introduced.
- Dev-deployed server skips the private-lobby citizen check — What: a server deployed with `GAME_ENV=dev` (e.g. `./build-deploy.sh dev`; `deploy.sh` writes `GAME_ENV=${ENV}`) skips the creator-citizen start check for anyone calling `POST /api/start_game/:id` directly, through the dev-only bypass (`isPrivateLobbyCitizenGateBypassed`, `src/server/GameServer.ts`); production and staging are unaffected, and an unset `GAME_ENV` keeps the check on · Why (structural): the bypass exists so private lobbies can be hosted on dev at all — the standalone dev page has no Yandex identity (review R2, owner ruling 2026-09-27 "Dev-only bypass"); the dev server is internal; without the bypass nobody could host a private lobby on dev; owner ruling 2026-09-27 "Accept: dev server is internal (Recommended)", relayed by fkit-lead · Re-raise only if: real players can reach the dev server (e.g. a Yandex draft or a public link pointed at it), or the bypass is keyed on anything other than an explicit `GAME_ENV=dev`.
- Stale Start can act on a reopened host modal — What: if the host closes and reopens the host modal while an earlier Start is in its network phase (settings save, then `start_game`, which can wait up to 5 s on the server's citizen check), that earlier attempt still runs against the new opening: a success closes the new modal, a failure shows the "couldn't start" line on it, and a settings save still pending when the new lobby id lands can send `start_game` for the NEW lobby with no tap. The `openGeneration` guard covers only the wait on the ad (`attemptStart()` in `src/client/HostLobbyModal.ts`) · Why (structural): it needs a close and reopen inside a few seconds of pressing Start; no data is harmed and the host can retry; the main hazard (reading a changed `lobbyId` across awaits) predates 0302; closing it fully means re-checking the generation after every await or carrying the lobby id through the whole flow, a wider rework of the start flow than this task's scope; owner ruling 2026-09-27 "Accept as known (Recommended)", relayed by fkit-lead (review R8) · Re-raise only if: players report lobbies closing or starting on their own, or the host-modal start flow is reworked.
