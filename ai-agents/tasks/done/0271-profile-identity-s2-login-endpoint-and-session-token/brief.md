## What to build

Per design §9 S2:

1. **`src/core/profile/LoginContract.ts`** — request `{ platform, platformUserId }` (1–128 chars),
   response `{ created, profile, grantChecks.tenure, session { token, expiresAt } }`; error codes
   `400 bad_request` · `503 session_unavailable` · `500 internal_error` (`503 creation_paused` is S5's).
2. **`POST /v1/login`** — validation, `resolveOrCreatePlayer` (S1), `created`, `grantChecks.tenure`
   (`done` iff a tenure grant row exists, any amount), public profile (no platform id, no player id),
   token. **No limiter.**
3. **`SessionToken` module** — `v1.<payload>.<HMAC-SHA256>`, payload `{pid, plt, iat, exp, vfy:false}`,
   TTL 24 h, constant-time MAC compare (the `InternalAuth.ts` pattern).
4. **`resolveCaller`** = valid Bearer token first → legacy Yandex-id fallback (**find-only, never
   creates**) → `401` with `session_expired` / `session_invalid`. Every public route takes its caller
   from it. Payments intent uses it too.
5. **CORS:** `Authorization` allowed and `Access-Control-Max-Age` set on all public routes; `OPTIONS`
   answers 204.
6. **`PROFILE_SESSION_SECRET`** — generated by `setup-profile.sh` into the 0600 env file, forwarded by
   `build-deploy-profile.sh` if it forwards env, added to `scripts/config-parity-allowlist.json`, and
   asserted by `tests/scripts/profile-deploy-hardening.test.sh`. **Fail closed:** empty → login and
   token routes `503 session_unavailable` plus a boot `warn` naming the variable, never its value.
   ⚠️ Coordinate with `0220`'s persist-or-reuse pattern for box secrets — a secret regenerated on every
   deploy only forces a silent re-login (no data loss), but decide it in the plan, don't leave it
   accidental.

**Default unless the owner rules otherwise (design §8 Q4):** keep `platformUserId` validation at
1–128 characters until real Yandex ids are sampled.

## Verification steps

1. Two parallel logins for one new identity → **one player** (integration test).
2. Token tampered / expired / signed with the wrong key / wrong version prefix → each `401` with the
   right code (unit tests).
3. The legacy Yandex-id fallback still serves existing callers, and **never creates** a player.
4. Secret unset → login `503 session_unavailable`; boot warning names the variable and contains no
   value.
5. No token, Yandex id or player id appears in any log line (test asserting over captured log output).
6. CORS preflight with `Authorization` answers 204 with `Max-Age`.
7. `npm test` (including the shell harnesses — CLAUDE.md consequence 1) and `npm run test:integration`
   green; `npx tsc --noEmit`, `npm run lint`, `npm run check:config-parity` clean for the new variable.
8. **On the box after the owner's deploy:** a login returns a token, and a `GET /v1/profile` with that
   Bearer token succeeds.

### Verification step 8 — both halves now met

*"a login returns a token, and a `GET /v1/profile` with that Bearer token succeeds"*

| Check | Result |
|---|---|
| First login, synthetic id | `created=true`, `grantChecks.tenure="pending"`, **token received** |
| **`GET /v1/profile` with that Bearer token** | **200**, full profile body (`xp`, `is_citizen`, `display_name`, `schema_version`, timestamps) — **acceptance proven** |
| Token with one character altered | **401** — the signature is genuinely verified, not decorative |
| `Authorization: bearer …` (lowercase prefix) | **401** — strict `Bearer ` parsing confirmed live. This was **S2 residual R3**, now settled |
| Second login, same id | **`created=false`** — find-or-create correct, no duplicate profile |
| Synthetic id in container logs | **0 occurrences** |
| Any session token in container logs | **0 occurrences** |
| Error-level log lines since boot | **0** |
| Cleanup (one transaction) | `DELETE 1` → back to **0 players, 0 identities** |

**Why the second row mattered.** Signing a token and verifying one are separate paths in `SessionToken`,
and `resolveCaller` is the piece every public route depends on. A token that is issued but not accepted
would have presented exactly as the box did before this run, and would have surfaced only once the
client shipped under `0273`. The earlier 401 on an **unauthenticated** `/v1/profile` proved the legacy
fallback was gone; it said nothing about Bearer acceptance. It does now.
