## Accepted residuals (shared, do-not-re-litigate)

- **No per-attempt timeout on a loader re-download** (R3, owner ruling 2026-09-28 "Accept as known") — What: each re-download is awaited until its own `load`/`error` fires; a re-download that stalls without ever settling holds back the remaining retries and the `Session:SdkLoaderRetry:GaveUp` event for as long as it stalls. Boot is unaffected: the unchanged 5 s platform-init deadline still bounds it. · Why (structural): the only way to cap an attempt is to abandon the pending tag and insert a new one, and that is unsafe — an `async` script whose fetch has started still executes when its download finishes, even after its tag is removed, so the loader could run twice and `YaGames` could be defined twice. Waiting for a settle is the price of the hard rule "retry only after `onerror`, never run the loader twice". Rejected: a per-attempt timeout with re-insert (double-execution risk); a timeout that only logs `GaveUp` without re-inserting (reports a give-up while a download may still succeed, and adds a second terminal path for little gain). · Re-raise only if: analytics show many first-failure pages with no `Session:SdkLoaderRetry:*` outcome beyond what early page closes explain (see the R2 caveat in the analytics reference), or a way appears to cancel an in-flight script fetch so it cannot execute.
