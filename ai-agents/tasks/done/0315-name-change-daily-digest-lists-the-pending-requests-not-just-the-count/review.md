The `…and M more` line can name requests that do not exist. If requests are decided or withdrawn between the heartbeat's count query and the list query (a window that spans the heartbeat's Telegram send and any retry), the list comes back shorter than the count, and `known` still takes the stale count. Measured: count 5 with 3 rows fetched printed 3 lines plus `…and 2 more waiting`, although the fresh read found only 3. When `entries.length < PENDING_LIST_CAP`, the fetched list is the complete set of pending requests at the moment it was read, so the fresher number is `entries.length`. That item is correct: it matches the literal formula whenever `entries.length <= count`, and is strictly better when the count raced low while rows were also dropped for length. Impact: a phantom "N more" on a rare day. The operator looks for requests that are not there, and the next day's list is correct. Nothing is decided wrongly. Direction: when the list is under the cap, count the remainder from the list rather than from the heartbeat. |
