## Accepted residuals (shared, do-not-re-litigate)
- **Tenure grant amount is capped only at the route** (R3; owner, 2026-09-15) — What: `POST /v1/profile/tenure-grant` is the only place the amount is computed and capped (`evaluateTenureClaim`). `PlayerProfileRepository.grantTenureXp` trusts `xpAwarded`, and `player_xp_grants` only checks `xp_awarded > 0`. · Why (structural): ADR-112 rule 3 names the server route as the single place the amount is computed. Rejected alternatives: a table CHECK would tie migration 005 to the tenure constant, and every future grant kind would need its own bound; a second cap in the repository would duplicate the rules in two places. Today there is exactly one caller. · Re-raise only if: a second caller of `grantTenureXp` (or of any grant-recording write) is added, or a second grant `kind` is added to `player_xp_grants`.
- **Fixed tenure claim window** (coder residual CR4 / worklog R4; owner, 2026-09-15) — What: the claim window is a code constant, `TENURE_WINDOW_OPENS_AT_MS` = 2026-09-19 00:00 Moscow time, open 90 days. If `0217` XP go-live slips, part of the window passes with every claim a temporary `no_credited_match`. · Why (structural): owner ruled "90 days is plenty". A constant needs no config plumbing and no server-side go-live record. Rejected alternative: a window that follows go-live through config. · Re-raise only if: `0217` go-live slips far enough to eat a meaningful share of the 90 days. The remedy is then a small change to the date constant, not a redesign.
