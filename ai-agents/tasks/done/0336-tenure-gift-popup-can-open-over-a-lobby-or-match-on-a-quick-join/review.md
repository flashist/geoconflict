## Accepted residuals (shared, do-not-re-litigate)
- **Matchmaking wait is not marked as joining** — What: `MatchmakingModal` (search, then a 3 s `/exists` poll) sends `join-lobby` with no `beginJoiningLobby()` marker, so a tenure popup that becomes ready during it could open over the matchmaking window. Nothing built. · Why (structural): unreachable today — `enableMatchmaking()` returns `false` in `DefaultConfig.ts` and no environment config overrides it, so `<matchmaking-button>` renders nothing and `<matchmaking-modal>` is never in the page. A whole-wait marker cannot be paired on the ✕ path without a behaviour change (o-modal's ✕ never reaches `MatchmakingModal.close()`, so its socket and 3 s poll keep running — pre-existing bug); a per-poll marker pairs cleanly but leaves the gaps between polls uncovered. Owner ruling 2026-09-30, "Record it, build nothing", via `AskUserQuestion` in the `fkit lead` session (0336 review R1, Matchmaking half). · Re-raise only if: `enableMatchmaking()` ever returns `true` — then cover the whole wait together with fixing the ✕ close bug.
- **A hung Join lookup holds the tenure popup** — What: `JoinPrivateLobbyModal.joinLobby()` keeps its joining marker until its `/exists` lookup (and, when not active, the archive + `commit.txt` fetches) settle; those fetches have no timeout, so a hung lookup holds a waiting popup until the browser gives up — even if the player closed the Join window. · Why (structural): the marker must end exactly once, after the lookup settles, so a found lobby hands off to Main's own marker without a gap; ending it on window close instead would add a second end path for a rare hang, and adding fetch timeouts is outside 0336's scope. Same shape as the owner-accepted §1e residual (a hung `createLobby`). XP is kept either way; only the thank-you's timing moves. Owner ruling 2026-09-30, "Accept both", via `AskUserQuestion` in the `fkit lead` session (0336 review R1 follow-up). · Re-raise only if: players report the popup never appearing after a Join, or the lobby lookups gain a timeout / abort path (then end the marker on it).
- **After a failed Join lookup the popup can open over the Join window** — What: when the lookup ends with "not found", "version mismatch", an error or a throw, the marker ends and, with the player on the start screen, a waiting tenure popup opens — on top of the still-open Join window showing its error message. · Why (structural): the player is not in a lobby or match, which is the only thing the brief forbids; holding the popup until the Join window closes would need a new "window open" signal for a rare overlap, and the popup is dismissible. Same shape as §1e's failed-create case (popup over the failed host window). Owner ruling 2026-09-30, "Accept both", via `AskUserQuestion` in the `fkit lead` session (0336 review R1 follow-up). · Re-raise only if: the popup must also never cover start-screen windows (a product change), or players report it hiding the Join error.
- **Tenure popup open at match start loses its restart follow-up on an in-page leave** — What: `TenureGrantModal.close()` (Main's pre-start close list) drops `onClosed`, so for a gift that made the player a citizen, `dispatchCitizenshipGrantedMidSession("tenure")` never fires if the popup was open when the match started; no restart offer appears. **Premise corrected:** "the page reloads after a match" is not always true — an in-page Back/hash leave mid-match (`onHashUpdate` → `handleLeaveLobby()`) does not reload, and on that path the follow-up is lost. (A popup only *held back* at match start does show on that leave and fires the follow-up.) · Why (structural): same settled shape as 0303's `onMatchStarting()` drop; rare × rare (popup open at match start needs a join that began without a tap on the overlay) × a mid-match Back/hash leave; XP and citizenship are unaffected — only the restart prompt is lost, and the next page load reads citizenship fresh. Rejected: re-firing `onClosed` on close (fires a follow-up mid-match), or storing a pending follow-up (new state for a rare path). Owner ruling 2026-09-30, "Accept, fix the record", given via `AskUserQuestion` in the `fkit lead` session (0336 review R2). · Re-raise only if: 0303's `onMatchStarting()` drop is revisited, or in-page leaves mid-match become a common path (e.g. a Back button in the match UI).
