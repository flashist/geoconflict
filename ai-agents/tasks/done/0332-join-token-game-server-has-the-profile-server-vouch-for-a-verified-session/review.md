| R1 | 1     | medium | src/server/GameServer.ts:1505-1521 (`acceptProfileSession`) + :1571-1582 (chain in `startProfileResolve`) | No limit on how many tokens one socket can submit. `acceptProfileSession` takes every token that differs from the one held, and each one queues another resolve behind the last, with the token captured at queue time. So a client sending `update_identity` with tokens A, B, C… (or just switching between two) drives one `POST /internal/v1/players/resolve` per message: a `find-or-create` against the profile DB, plus a `resolve.vouch{invalid}` count. The queue and the tokens it holds also grow in game-server memory while the profile server is slow. Before 0332, `update_identity` could trigger at most one resolve per client (only the id's null→value change did it). Measured with a scratch probe on the real `GameServer`: 50 distinct-token messages → **51** `resolvePlayer` calls, run one after another. Impact: a cheap way to load the low-RAM profile box, and it pollutes the counter that ADR-124's re-raise trigger 2 and the verify task read. Players see nothing. Direction (coder's call): cap the token attempts per `Client`, and/or have a queued resolve read the *latest* held token when it runs, so queued resolves collapse into one. |

## Accepted residuals (shared, do-not-re-litigate)
- **Token over 24 h old sent at join (R2)** — What: the client sends a held session token in the join without checking its age; a token past its 24 h TTL is vouched `expired`, dropped, and the late send never runs, so that player stays `unverified` for the rest of that socket. · Why (structural): `ProfileSession` never decides on expiry on purpose (a wrong device clock must not force a login before every call); fixing it inside 0332 would mean a client-side age check or a re-login path. The owner ruled (2026-10-07) that the right fix is a separate one: a popup that asks the player to restart / refresh the page after about 24 h of play, shown only on the main screen and never breaking an active match. Rejected here: a client-side `expiresAt` check (clock-dependent, against the D-ruling in `ProfileSession.ts`), and a forced `ensureSession()` re-login at join (adds login waits to the join path). Today it shows only as `expired` / `unverified` in the counters; every use is `allow`. · Re-raise only if: task `0404` (the Sprint 8 restart-after-~24 h popup) is cancelled or ships without covering this; OR any of the four uses moves off `allow` (enforcement, slice B) before that task ships; OR the counters after deploy show `expired` as a large share of vouches.
