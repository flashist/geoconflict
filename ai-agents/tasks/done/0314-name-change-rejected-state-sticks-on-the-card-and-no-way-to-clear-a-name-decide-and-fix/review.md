## Accepted residuals (shared, do-not-re-litigate)
- **Decline after a clear shows idle** (R1, owner-accepted 2026-09-27, "Accept it (Recommended)") — What: when an operator clears a player's approved name while that player has a pending request, the clear leaves the request alone; if the operator later *rejects* that request, the newest non-pending row is still the `cleared` one, so `getLatestState` returns null and the card shows its idle state instead of the declined notice. The reason still reaches the player's inbox, and idle is the same state the Hide button would lead to. · Why (structural): the card projects ONE row, chosen by `LATEST_SQL` (pending first, else newest by id), and the Hide button's `DISMISS_REJECTION_SQL` must pick the same row or Hide silently no-ops and Gap 1 returns. A fix means changing both orderings together (e.g. by decision time) — two coupled rules to keep in step, for a case that needs an operator clear and a pending request on the same player at once. Owner ruled it harmless and rare. Rejected: re-ordering both queries by decision time now (coupling risk, no reported harm). · Re-raise only if: players report it, or the name-change state model is reworked.
