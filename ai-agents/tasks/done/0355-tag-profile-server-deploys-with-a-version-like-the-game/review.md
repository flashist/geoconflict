## Accepted residuals (shared, do-not-re-litigate)
- **R3 — the dirty gate is a git-status check, not a proof that the image equals the commit** — What: the refuse-on-dirty gate runs `git status --porcelain --untracked-files=normal -- <PROFILE_SHIPPED_PATHS>` once, before the build. It cannot see gitignored files under `src/` that `COPY src` still ships (today `src/.DS_Store`, `src/client/.DS_Store` — `.dockerignore`'s `.DS_Store` matches only the root), it names `package.json package-lock.json` while `Dockerfile.profile` copies the glob `package*.json`, and the build reads the live tree after the check (an edit in between ships unseen). The code comment says exactly this. · Why (structural): owner ruling 2026-09-30 ("Fix the wording, accept"), relayed by `fkit-lead` in the `fkit-sprint-ship-loop` round-1 review step. Closing it means building from a clean export of `GIT_COMMIT` (`git archive` / a worktree) — a change to the build input the plan did not include — or widening `.dockerignore` + the pathspec, which narrows but does not close the check-then-build window. Secrets are covered separately by the byte scan of the built image. · Re-raise only if: a gitignored or post-check file that is **not** harmless (code, config, a migration) is found shipped in a profile image, or the owner asks for commit-exact images.
- **Limit 1 — the counter is picked before the lock (same-name race, including across machines)** — What: `N` is computed before the build; the deploy lock (a local `mkdir` mutex) is taken after the push. Since R2 was built (owner ruling 2026-09-30, Option 1) the **registry is the shared claim point**: the name is checked free before the build and again right before the push, and a taken name stops the push — so two deploys can no longer both push one name, **except** in the short window between one deploy's second check and its `docker push` (Docker has no "push only if new"). If that window is hit, the later push silently replaces the earlier deploy's registry label `:.N`, and **nothing guarantees a visible signal** (wording corrected in round 2, finding R9). Traced on one machine: A pushes `.N` → A's post-push check matches (no warning) → B, whose re-check ran before A's push, pushes `.N` over it → B stops at the `mkdir` lock ("another profile deploy is already running") and never tags → A deploys and git-tags `.N`. Result: git tag `.N` = A's commit, registry `:.N` = B's never-deployed image, **no WARNING anywhere** — only B's lock error. A WARNING appears only if the overwritten deploy's post-push check happens to run after the other push; across two machines (no shared lock) both may deploy and the second git tag then fails (`tag-failed` / `push-failed`, warned, never forced). The box always runs the digest it was given, so content is never wrong — only the registry label can point at the wrong image. Two images that both baked the name before either pushed can also both *report* it on `/health`. · Why (structural): owner ruling 2026-09-30 ("Accept all three"), relayed by `fkit-lead`; plan §6 accepted this shape. Closing the last window needs an atomic "create tag only if absent" that the registry API does not offer through `docker`. · Re-raise only if: two profile deploys are ever run concurrently (from one machine or two) — including a deploy stopped by "another profile deploy is already running" **after** its push — the post-push "resolves to … not this build's" WARNING is ever seen, or two different images are seen carrying one version name.
- **Limit 2 — a pushed-but-never-deployed image keeps its name in the registry** — What: if the push succeeds but the deploy stops before the lock/record (e.g. the digest cannot be resolved), that image stays in the registry under its version name `.N`, no record line claims `.N`, and it never gets a git tag. Since R2 was built (owner ruling 2026-09-30, Option 1) the next deploy **does not reuse `.N`**: the registry check sees the name held and skips to `.N+1` (T34/T35). So the registry can hold version names with no git tag and no record line — each is an attempt that was pushed and never deployed. · Why (structural): owner ruling 2026-09-30 ("Accept all three"), relayed by `fkit-lead`. A registry name means "built and pushed as attempt N", not "deployed" — the git tag carries "deployed OK", and the digest + record stay the trust anchor. Recording the attempt before the push would mean moving the lock and record ahead of the build, which was not in the plan. · Re-raise only if: a version name is ever found on two different digests, or a registry name with no record line is mistaken for a deploy.
- **Limit 3 — the remote-tag read needs the network, else it only warns** — What: `git ls-remote --tags origin` feeds the counter; if it fails, the deploy warns and numbers from local tags + the deploy record only (T29). · Why (structural): owner ruling 2026-09-30 ("Accept all three"), relayed by `fkit-lead`. Refusing to deploy with no remote read would block an urgent deploy on a network blip for a cosmetic label; a clash that slips through surfaces as a failed tag push (warned, never forced). · Re-raise only if: a remote-read failure is ever followed by a duplicate version name, or the owner wants the deploy to refuse when it cannot read remote tags.
